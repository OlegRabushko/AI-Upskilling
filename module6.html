Модуль 6

Tools и MCP

До сих пор бот только отвечал. Теперь он начнёт действовать: искать в базе, создавать тикеты, проверять статус. Вы освоите tool calling, безопасный вызов инструментов и стандарт MCP (Model Context Protocol).

Опора на llm_client.py и RAG из модуля 5. Для MCP: pip install mcp.

Задание 6.1

Tool calling

Что делаем: даём модели одну функцию и позволяем ей решить, когда её вызвать. Зачем: это переход от «текста» к «действию» — модель выбирает инструмент, но выполняет его ваш код.

Шаг 1Обычная функция

def get_ticket_status(ticket_id: str) -> str:
    fake = {"T-1": "open", "T-2": "resolved"}
    return fake.get(ticket_id, "not found")

Шаг 2Описание инструмента для модели 

TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_ticket_status",
        "description": "Вернуть статус тикета по его id",
        "parameters": {
            "type": "object",
            "properties": {"ticket_id": {"type": "string"}},
            "required": ["ticket_id"],
        },
    },
}]

Шаг 3Первый вызов — модель просит инструмент 

import json
from openai import OpenAI
client = OpenAI()

messages = [{"role": "user", "content": "Какой статус у тикета T-1?"}]
r = client.chat.completions.create(
    model="gpt-4o-mini", messages=messages, tools=TOOLS)
msg = r.choices[0].message
print(msg.tool_calls)   # модель вернула запрос на вызов функции

Шаг 4Выполняем и возвращаем результат 

messages.append(msg)
for call in msg.tool_calls:
    args = json.loads(call.function.arguments)
    result = get_ticket_status(**args)     # выполняет НАШ код, не модель
    messages.append({"role": "tool", "tool_call_id": call.id,
                     "content": result})

final = client.chat.completions.create(model="gpt-4o-mini", messages=messages)
print(final.choices[0].message.content)

Шаг 5Когда инструмент не нужен 

r = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Привет, как дела?"}],
    tools=TOOLS)
print(r.choices[0].message.tool_calls)   # None — модель отвечает текстом
Вывод: модель лишь предлагает вызов с аргументами; решение выполнять — за вашим кодом.
Задание 6.2

Несколько инструментов и маршрутизация

Что делаем: добавляем поиск и создание тикета, строим общий цикл. Зачем: реальному агенту нужно выбирать из нескольких инструментов и вызывать их по цепочке.

Шаг 1Набор инструментов

TICKETS: dict = {}

def search_kb(query: str) -> str:
    return f"Найдено в базе по запросу '{query}'"

def create_ticket(title: str, priority: str = "medium") -> str:
    tid = f"T-{len(TICKETS) + 1}"
    TICKETS[tid] = {"title": title, "priority": priority, "status": "open"}
    return tid

FUNCS = {"search_kb": search_kb, "create_ticket": create_ticket,
         "get_ticket_status": get_ticket_status}

Шаг 2Описания всех инструментов 

TOOLS = [
    {"type": "function", "function": {
        "name": "search_kb", "description": "Поиск по базе знаний",
        "parameters": {"type": "object",
            "properties": {"query": {"type": "string"}}, "required": ["query"]}}},
    {"type": "function", "function": {
        "name": "create_ticket", "description": "Создать тикет поддержки",
        "parameters": {"type": "object", "properties": {
            "title": {"type": "string"},
            "priority": {"type": "string", "enum": ["low", "medium", "high"]}},
            "required": ["title"]}}},
    {"type": "function", "function": {
        "name": "get_ticket_status", "description": "Статус тикета",
        "parameters": {"type": "object",
            "properties": {"ticket_id": {"type": "string"}},
            "required": ["ticket_id"]}}},
]

Шаг 3Единый цикл агента

def agent(user_msg: str) -> str:
    messages = [{"role": "user", "content": user_msg}]
    for _ in range(5):                       # ограничиваем число шагов
        r = client.chat.completions.create(
            model="gpt-4o-mini", messages=messages, tools=TOOLS)
        msg = r.choices[0].message
        if not msg.tool_calls:
            return msg.content               # финальный ответ
        messages.append(msg)
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            result = FUNCS[call.function.name](**args)
            messages.append({"role": "tool", "tool_call_id": call.id,
                             "content": str(result)})
    return "Превышено число шагов."

Шаг 4Проверяем маршрутизацию 

print(agent("Создай тикет: не открывается отчёт"))
print(agent("Какой статус у T-1?"))

Шаг 5Цепочка из двух инструментов 

print(agent("Найди в базе про отпуск и заведи тикет на обновление статьи"))
print("Созданные тикеты:", TICKETS)
Вывод: цикл «запрос → вызовы инструментов → результаты → ответ» — ядро любого tool-агента. Лимит шагов защищает от бесконечных циклов.
Задание 6.3

Безопасный вызов инструментов

Что делаем: добавляем валидацию, allowlist и подтверждение опасных действий. Зачем: модель не должна бесконтрольно выполнять операции, меняющие данные.

Шаг 1Allowlist инструментов

ALLOWED = {"search_kb", "create_ticket", "get_ticket_status"}

def guard_name(name: str):
    if name not in ALLOWED:
        raise PermissionError(f"Инструмент '{name}' запрещён")

Шаг 2Валидация аргументов

def validate_create(args: dict):
    title = args.get("title", "")
    if not title or len(title) > 200:
        raise ValueError("Некорректный title")
    if args.get("priority", "medium") not in {"low", "medium", "high"}:
        raise ValueError("Некорректный priority")

Шаг 3Подтверждение опасных операций 

def needs_confirmation(name: str, args: dict) -> bool:
    return name == "create_ticket" and args.get("priority") == "high"

def confirm(name: str, args: dict) -> bool:
    # в реальном UI — кнопка; здесь имитируем ручное согласие
    print(f"Подтвердите действие {name} {args} (y/n)")
    return input().strip().lower() == "y"

Шаг 4Безопасный исполнитель

def safe_execute(name: str, args: dict) -> str:
    guard_name(name)
    if name == "create_ticket":
        validate_create(args)
    if needs_confirmation(name, args) and not confirm(name, args):
        return "Действие отменено пользователем."
    return str(FUNCS[name](**args))

Шаг 5Встраиваем в цикл агента 

# в цикле из 6.2 замените вызов FUNCS[...] на:
#   result = safe_execute(call.function.name, args)
print(safe_execute("create_ticket", {"title": "Срочно", "priority": "high"}))
print(safe_execute("delete_db", {}))   # поднимет PermissionError
Вывод: allowlist + валидация + подтверждение — минимальный безопасный контур для tool-агента. Подробнее о безопасности — в модуле 8.
Задание 6.4

MCP: свой сервер

Что делаем: выносим инструменты в отдельный MCP-сервер. Зачем: MCP — стандарт, по которому любой агент (Claude Code, Cursor и др.) может подключать ваши инструменты без переписывания.

Шаг 1Минимальный MCP-сервер

# файл: kb_mcp_server.py
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("knowledgebot")

@mcp.tool()
def search_kb(query: str) -> str:
    """Поиск по базе знаний KnowledgeBot."""
    return f"Найдено по '{query}'"

Шаг 2Добавляем инструмент тикетов 

_TICKETS: dict = {}

@mcp.tool()
def create_ticket(title: str, priority: str = "medium") -> str:
    """Создать тикет поддержки и вернуть его id."""
    tid = f"T-{len(_TICKETS) + 1}"
    _TICKETS[tid] = {"title": title, "priority": priority, "status": "open"}
    return tid

Шаг 3Запуск сервера

if __name__ == "__main__":
    mcp.run()   # сервер общается по протоколу MCP (stdio)
python kb_mcp_server.py

Шаг 4Регистрация в агенте

// пример записи в конфиге MCP-клиента (напр. Claude Code)
{
  "mcpServers": {
    "knowledgebot": {
      "command": "python",
      "args": ["kb_mcp_server.py"]
    }
  }
}

Шаг 5Проверка

В агенте спросите:
"Через knowledgebot создай тикет 'Обновить FAQ про отпуск'."
Агент вызовет инструмент create_ticket на вашем MCP-сервере.
Вывод: описав инструмент один раз как MCP-сервер, вы делаете его доступным любому MCP-совместимому агенту.
Задание 6.5

MCP: подключение к реальной системе

Что делаем: подключаем готовый GitHub MCP и управляем задачами из агента. Зачем: ценность MCP — в доступе к настоящим системам (GitHub, Jira, БД) без своей интеграции.

Шаг 1Подключаем GitHub MCP

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
Токен берётся из переменной окружения — не вписывайте его в конфиг напрямую (см. модуль 8).

Шаг 2Читаем issues из агента 

Промпт агенту:
"Покажи открытые issues в моём репозитории knowledgebot."

Шаг 3Создаём задачи по спецификации 

Промпт:
"Создай 3 issue по нереализованным фичам из spec/: RAG, tools, security."

Шаг 4Свой MCP + внешний MCP вместе 

Промпт:
"Через knowledgebot создай тикет на баг, затем через github заведи issue
с тем же заголовком и дай ссылку."

Шаг 5Безопасность доступа

Чек-лист перед подключением внешнего MCP:
- выдан минимальный scope токена (только нужные права);
- токен — в переменной окружения, не в конфиге;
- опасные действия требуют подтверждения;
- логируются все вызовы инструментов.
Итог модуля: KnowledgeBot умеет действовать — локально и во внешних системах через MCP. В модуле 7 соберём из этого управляемый многошаговый workflow.
